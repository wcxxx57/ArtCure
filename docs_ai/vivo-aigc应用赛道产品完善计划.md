# vivo AIGC 应用赛道产品完善计划

> 项目：艺术疗愈小程序 / ArtCure  
> 目标：基于现有微信小程序与微信云开发能力，扩展为面向 vivo AIGC 创新赛应用赛道的「手机 AI 艺术疗愈助手」方案。  
> 生成日期：2026-05-02

## 1. 结论先行

当前项目已经具备较好的参赛基础：原生微信小程序页面、微信云函数、艺术疗愈 RAG 服务、疗愈馆资源推荐、心情记录与计划生成等模块都已经存在。最适合的比赛叙事不是“做一个心理聊天机器人”，而是升级成：

**艺哟：面向 vivo 手机的多模态艺术疗愈 AI 助手**

核心卖点：

- 用户可以用文字、短语音、绘画照片、地理位置与 AI 互动。
- AI 能理解用户当前情绪，并调用艺术疗愈知识库、语音生成、OCR/多模态理解、POI 检索等能力，给出低风险、非诊断式的疗愈陪伴。
- 产品不是替代心理咨询，而是提供日常情绪觉察、创作引导、线下疗愈资源发现、疗愈计划执行。

形态建议：

- **初赛/近期实现**：保留现有微信小程序为主形态，在 vivo 手机上通过微信运行；先把 vivo AI API 接入到微信云函数，快速做出可演示能力。
- **复赛/更贴合 vivo 生态**：优先补一个 **快应用或轻量 Android App 壳**。快应用更贴合 vivo 手机与系统入口，App 更容易调用系统能力与展示端侧化思路。
- **智能体**：建议作为入口/补充，而不是唯一作品形态。智能体负责“唤起艺哟、记录心情、开始一次语音疗愈、推荐附近资源”，完整体验仍落到小程序/快应用/App 页面。

## 2. 资料访问状态

当前环境能打开入口页面，但页面正文是前端 JavaScript 渲染，文本抓取没有拿到具体接口参数。本地直接请求 vivo 开发者文档资源时，由于外部网络审批超时，也未能进一步抓取。暂时无法确认是否必须登录才能查看全部文档。

可从公开资料和第三方 SDK 文档交叉确认的能力包括：

- 蓝心大模型 70B、蓝心大模型多模态、AI 绘画
- 通用 OCR
- 实时短语音识别、长语音听写、长语音转写
- 音频生成 TTS、声音复制/拟人音色
- 文本翻译、文本向量、文本相似度、查询改写
- 地理编码与 POI 搜索

后续执行前需要 wcx 登录 vivo 文档确认：鉴权方式、请求域名、签名算法、音频/图片大小限制、QPS/额度、是否允许服务端转发、是否有小程序/快应用特定接入限制。

## 3. 现有项目盘点

### 3.1 当前技术结构

当前项目是：

- `miniprogram/`：原生微信小程序，页面以 `.wxml`、`.wxss`、`.js`、`.json` 组织。
- `cloudfunctions/`：微信云函数，已经有登录、注册、AI 对话、心情推荐、疗愈计划、疗愈资源、活动、支付等函数。
- `ai-server/`：独立 FastAPI 服务，使用 FAISS + BGE 向量检索 + DeepSeek/OpenAI 兼容接口生成回复。
- `docs_ai/`：已有 RAG、疗愈馆、知识库、部署等说明文档。

### 3.2 已有产品能力

已有能力可以直接进入比赛叙事：

- AI 聊天页：树洞模式、疗愈师模式、日常陪伴模式。
- 疗愈馆：本地资源数据、筛选、活动、资源详情。
- AI 资源顾问：`healing-hall-ai-advisor` 已有专门对话页，可走 `wx.cloud.callFunction({ name: 'askAI' })`。
- 心情推荐：基于心情记录生成疗愈计划。
- 计划生成：可生成多天疗愈任务。
- 资源数据：包含疗愈方式、价格、地点、联系方式、来源平台、标签等字段。

### 3.3 当前需要优先修正的工程点

这些点不一定影响概念展示，但会影响真实可运行与评审稳定性：

- `miniprogram/pages/ai-chat/index.js` 仍直接请求 `http://127.0.0.1:8000`，真机和线上环境不可用，也不符合项目约定的“前端通过云函数调用后端”。
- `cloudfunctions/planGenerator/index.js` 和 `cloudfunctions/moodRecommendation/index.js` 中存在硬编码 AI 服务地址与 API Key，后续应移动到云函数环境变量。
- `healing-hall` 当前主要读本地样例数据，正式推荐应逐步迁移到云数据库与语义检索。
- `ai-server` 需要公网 HTTPS 或被云函数替代，否则微信真机调试和比赛演示风险较高。
- 项目已有不少未提交/新增文件，执行前要避免覆盖 wcx 已有改动。

## 4. 总体产品方案

### 4.1 产品定位

名称建议：

- 艺哟 ArtCure
- 艺哟疗愈助手
- vivo 艺疗小 V

一句话：

**把手机变成随身艺术疗愈陪伴者：能听你说、看你画、懂你的位置，并把情绪转化为可执行的创作练习和附近疗愈资源。**

### 4.2 用户主流程

1. 用户打开应用，选择“今天我想被陪伴 / 想做创作 / 想找附近资源”。
2. 用户用文字或语音描述状态。
3. AI 结合心情记录、历史对话、艺术疗愈知识库生成回应。
4. 如果用户上传绘画/手账/涂鸦照片，AI 通过 OCR/多模态能力提取文字和画面元素，生成非诊断式反馈。
5. 如果用户想线下体验，AI 结合当前位置、预算、时间、疗愈方式，推荐附近资源。
6. AI 生成一段可播放的短语音引导，用户可以闭眼跟随 3-5 分钟。
7. 结束后记录本次疗愈卡片，沉淀为个人疗愈轨迹。

## 5. vivo 能力与功能映射

### 5.1 文本相似度 / 文本向量 / 查询改写：艺术疗愈知识库

目标：

- 把现有 `ai-server/knowledge_base`、疗愈资源、活动、计划任务模板整理为可检索知识库。
- 用 vivo 文本向量或文本相似度替代/补充当前 BGE + FAISS。
- 用查询改写处理“我最近又那样了”“上次那个绘画方法”等上下文指代。

建议功能：

- “问艺哟”：用户提问艺术疗愈概念、方法、适用场景。
- “此刻适合的练习”：输入情绪，召回 3 个练习候选，通过相似度排序。
- “知识来源卡片”：每次回复展示 1-3 条引用来源，如“曼陀罗绘画适合整理思绪”“流体画适合释放压力”。

建议实现：

- 新增云函数 `vivoKnowledgeSearch` 或并入 `vivoAigcGateway`。
- 云数据库新增 `knowledge_chunks` 集合：
  - `chunkId`
  - `title`
  - `content`
  - `sourceType`
  - `therapyMedium`
  - `moodTags`
  - `embedding`
  - `updatedAt`
- 前端统一调用：

```js
wx.cloud.callFunction({
  name: 'vivoAigcGateway',
  data: {
    action: 'knowledge.search',
    query,
    scene: 'art_therapy_chat'
  }
})
```

执行步骤：

1. 整理知识库文档，切片成 300-600 字。
2. 批量调用 vivo 文本向量生成 embedding，写入云数据库。
3. 用户提问时先做查询改写，再召回候选。
4. 对候选用文本相似度二次排序。
5. 把 Top 3 作为上下文传给蓝心大模型或现有 RAG 生成回答。

优先级：P0。

### 5.2 短语音识别 + TTS/拟人音色：艺术疗愈语音陪伴

目标：

- 让用户像对手机 AI 助手说话一样进入疗愈。
- AI 生成 1-5 分钟短语音引导，例如呼吸、涂鸦、曼陀罗、睡前放松。
- 如果使用声音复制，必须增加明确授权与删除入口。

建议功能：

- “按住说心情”：短语音转文字，进入 AI 聊天。
- “听艺哟引导”：AI 回复后生成音频播放。
- “3 分钟绘画疗愈”：AI 语音引导用户拿起纸笔完成练习。
- “疗愈音色选择”：温柔女声、沉稳男声、儿童友好声线；声音复制作为高级演示能力。

建议实现：

- 小程序端使用 `wx.getRecorderManager()` 录音，上传临时文件到云存储。
- 云函数下载音频，必要时转换为 vivo 要求的 wav 16k/16bit/单声道。
- 调用短语音识别得到文本。
- 走 `askAI` / `vivoAigcGateway` 生成回复。
- 调用 TTS 生成 PCM/WAV，上传云存储，返回 `fileID` 或临时 URL。
- 小程序端用 `InnerAudioContext` 播放。

新增页面建议：

- `miniprogram/pages/voice-healing/index.wxml`
- `miniprogram/pages/voice-healing/index.wxss`
- `miniprogram/pages/voice-healing/index.js`
- `miniprogram/pages/voice-healing/index.json`

云函数建议：

- `cloudfunctions/vivoVoice/index.js`
  - `action: 'asr.short'`
  - `action: 'tts.create'`
  - `action: 'voice.clone.create'`
  - `action: 'voice.clone.delete'`

优先级：P0。声音复制为 P2，只有确认合规与时间充足后再做。

### 5.3 OCR + 多模态：绘画疗愈与心理分析

目标：

- 用户拍摄自己的绘画、手账、涂鸦、便签，AI 识别文字与画面内容。
- 输出“情绪线索观察 + 艺术疗愈练习建议”，避免诊断、贴标签或病理化。

建议功能：

- “上传今天的画”：识别画中文字、颜色、构图、主题。
- “画面里的情绪线索”：用温和语言描述观察，而不是判断用户心理疾病。
- “下一笔建议”：给出 3 个可执行创作动作，如“加一个安全色块”“给画面中的自己画一个边界”“写下这幅画想说的一句话”。
- “生成疗愈记录”：保存图片、AI 观察、用户自评心情。

建议实现：

- 小程序端 `wx.chooseMedia()` 选择图片。
- 上传云存储。
- 云函数 `vivoArtworkAnalyze`：
  - OCR 提取画中文字。
  - 蓝心多模态识别画面元素/颜色/构图。
  - 蓝心大模型生成结构化反馈。
- 云数据库新增 `artwork_sessions`：
  - `imageFileID`
  - `ocrText`
  - `visualTags`
  - `emotionHypotheses`
  - `suggestedExercise`
  - `userMoodBefore`
  - `userMoodAfter`
  - `createdAt`

输出模板：

```json
{
  "observation": "我注意到画面里有较多蓝色和封闭线条...",
  "possibleFeeling": "这可能和想要安静、边界感或休息有关，但不代表诊断。",
  "nextExercise": [
    "给画面加一个让你觉得安全的颜色",
    "在角落写一句此刻想对自己说的话",
    "用线条画出今天压力从哪里来、往哪里去"
  ],
  "safetyNote": "如果你持续强烈痛苦，请联系可信任的人或专业支持。"
}
```

优先级：P1。它最能体现“影像”场景和艺术疗愈差异化。

### 5.4 地理编码 / POI：疗愈实体线下资源推荐

目标：

- 从“资源列表”升级为“附近可到达的疗愈资源助手”。
- 结合用户位置、POI 搜索、现有资源库、价格/标签/评价，生成可执行推荐。

建议功能：

- “离我最近的绘画疗愈”
- “今晚下班后 30 分钟内可到的放松活动”
- “静安区 200 元以内适合新手的疗愈工作坊”
- “路线 + 电话/微信 + 预约建议”

建议实现：

- 小程序端申请 `wx.getLocation()` 权限，用户拒绝时可手动选择城市/区域。
- 云函数 `vivoGeoResource`：
  - 调用 vivo POI 搜索，例如关键词“艺术疗愈”“绘画工作坊”“心理咨询”“冥想”“颂钵”。
  - 将 POI 与 `healing_resources`/`shops` 集合按名称、地址、标签做匹配。
  - 用文本相似度匹配用户需求与资源描述。
  - 计算距离、价格、可信度、合作状态，生成排序。
- 小程序端展示资源卡片和地图入口。

评分建议：

```txt
finalScore =
  0.35 * semanticScore +
  0.20 * distanceScore +
  0.20 * resourceQualityScore +
  0.15 * priceFitScore +
  0.10 * moodFitScore
```

优先级：P1。它能贴合“出行/生活服务”场景，也能显著增强比赛完整度。

### 5.5 AI 绘画 / 图片外拓：疗愈意象生成

目标：

- 把用户情绪转化为可视化疗愈图像或创作灵感。
- 可作为锦上添花能力，不建议抢在语音和 OCR 前面做。

建议功能：

- “把今天的心情生成一张疗愈意象卡”
- “根据我的画继续外拓一个安全空间”
- “生成今日疗愈色卡”

优先级：P2。

## 6. 推荐系统架构

### 6.1 最小改动架构

保持微信小程序作为前端，所有 vivo API 调用放到微信云函数里：

```txt
miniprogram
  -> wx.cloud.callFunction
  -> cloudfunctions/vivoAigcGateway
  -> vivo AIGC API
  -> 云数据库/云存储
  -> miniprogram 渲染
```

优点：

- 不暴露 vivo AppID/AppKey。
- 符合项目约定：前端统一用 `wx.cloud.callFunction`。
- 能保留现有小程序页面和云开发体系。
- 后续迁移快应用/App 时，后端接口仍可复用。

### 6.2 中期架构

把当前 `ai-server` 作为“重检索与编排服务”，vivo 能力通过网关服务接入：

```txt
小程序/快应用/App
  -> 云函数 gateway
  -> ai-server/orchestrator
     -> vivo text vector / similarity / query rewrite
     -> vivo ASR / TTS / OCR / POI
     -> existing RAG / DeepSeek fallback
  -> 云数据库
```

注意：如果继续保留 `ai-server`，需要 HTTPS、公网域名、鉴权、超时与日志脱敏。

### 6.3 目标架构

如果比赛复赛开放端侧模型能力，可以把“敏感/高频/离线可用”的部分向端侧迁移：

- 端侧：意图识别、情绪自评、短提示词生成、最近记录摘要。
- 云端：多模态识别、TTS、POI、知识库长文本生成。
- 云数据库：用户授权后的疗愈记录、资源数据、缓存。

验收：

  - `chat.complete`

验收：

- 失败时返回统一结构：

```json
{
  "success": false,
  "code": "VIVO_API_TIMEOUT",
  "message": "服务暂时繁忙，请稍后再试"
}
```

### 阶段 3：知识库与文本相似度

目标：完成“艺术疗愈知识库”的比赛核心能力。

任务：

- 整理 `ai-server/knowledge_base` 为结构化 markdown/txt。

验收：

### 阶段 4：语音疗愈

目标：完成短语音输入与 TTS 输出闭环。

### 阶段 5：绘画疗愈分析

目标：完成影像场景能力。

- 新增绘画疗愈页。
- 图片上传云存储。

验收：

- 上传一张手账/涂鸦图片，能得到文字识别与创作建议。
- 页面明确声明“仅作为自我觉察与艺术疗愈参考，不构成心理诊断”。

### 阶段 6：POI 与线下资源推荐

目标：完成“出行/生活服务”能力。

任务：

- 接入位置授权。
- 用 POI 搜索补充真实地点。
- 与现有 `healing_resources`、`shops` 做匹配。
- 展示距离、价格、疗愈方式、联系方式。
- 增加“打开地图/复制地址/电话/微信”。

验收：

- 用户输入“附近 200 元以内绘画疗愈”，返回可到达资源。
- 用户拒绝定位时，可手动选城市/区域。

### 阶段 7：比赛形态增强

目标：从“微信小程序项目”升级为“vivo 手机 AI 体验作品”。

路线 A：快应用

- 重写核心页面为快应用页面。
- 复用云函数/HTTPS 后端。
- 保留小程序作为已有产品和备选演示。
- 适合强调 vivo 手机系统入口。

路线 B：Android App

- 用 WebView/原生壳承载 H5 版页面，或用跨端框架重写核心页面。
- 更容易演示系统权限、语音、文件、定位。
- 开发量比快应用略可控，但和“vivo 系统生态”结合感弱一点。

路线 C：智能体

- 做一个“艺哟疗愈智能体”，负责意图理解和打开对应页面。
- 适合作为入口，不建议替代完整应用。

验收：

- 能在 vivo 手机上运行核心流程。
- 答辩能展示“文字/语音/图片/位置”至少 3 种模态。

## 8. 形态是否需要从小程序更改

### 8.1 小程序能否参赛

从“能在 vivo 手机上运行”的角度，微信小程序可以在 vivo 手机上通过微信运行。但它不是 vivo 系统原生形态，也不天然体现蓝心小 V、AI OS、快应用等系统体验。

因此：

- **可以保留小程序作为最快 MVP 和真实产品底座。**
- **如果想在应用赛道更占优势，建议补一个 vivo 原生感更强的形态。**

### 8.2 各形态迁移成本

| 形态 | 推荐度 | 成本 | 优点 | 风险 |
| --- | --- | --- | --- | --- |
| 继续微信小程序 | 高，适合初赛 | 低 | 复用现有代码最快，功能完整 | vivo 系统体验不够强 |
| 快应用 | 高，适合复赛 | 中高 | 更贴近 vivo 手机生态，可作为系统级入口 | WXML/WXSS 不能直接复用，需要重写 UI |
| Android App | 中高 | 中 | 可稳定展示语音、图片、定位、后台能力 | 原生开发/打包链路需要补齐 |
| Web/H5 | 中 | 中 | 后端可复用，演示方便 | 和“手机系统 AI 体验”弱 |
| 智能体 | 中高，作为补充 | 中 | 很贴合手机 AI 助手 | 单独做不够承载复杂疗愈流程 |

### 8.3 推荐路线

建议采用“双层作品形态”：

1. **主体验：现有微信小程序升级版**  
   快速完成 vivo AI API 接入，保障功能完整、数据沉淀、页面成熟。

2. **vivo 展示层：快应用或轻量 App**  
   只实现 3 个高光入口：
   - 语音疗愈
   - 上传绘画分析
   - 附近疗愈资源

这样既不浪费现有小程序，也能让评委看到“最终能够在 vivo 手机上运行”的系统化设计。

## 9. 比赛演示脚本建议

3 分钟演示可以这样讲：

1. “我今天很焦虑，想找一个不用出门也能开始的方法。”  
   展示短语音识别 -> AI 回复 -> TTS 引导。

2. “我刚画了一张涂鸦，不知道它表达了什么。”  
   展示上传图片 -> OCR/多模态分析 -> 下一步创作建议。

3. “如果我周末想线下体验，附近有什么适合新手的？”  
   展示 POI + 资源库匹配 -> 推荐卡片 -> 复制微信/电话/地图。

4. “这不是医疗诊断，而是一个随身情绪觉察与艺术疗愈助手。”  
   展示安全边界和个人疗愈记录。

## 10. 数据与合规边界

必须明确：

- 不做心理疾病诊断。
- 不输出“你有抑郁症/焦虑症”等判断。
- 对自伤、自杀、严重危机内容给出求助提示和紧急联系人建议。
- 语音复制必须有明确授权、用途说明、删除入口。
- 绘画图片与语音默认只用于本次分析，保存需用户确认。
- 位置权限必须可拒绝，拒绝后提供手动城市/区域选择。

## 11. 需要 wcx 后续确认的设计点

执行代码前需要确认：

1. 最终参赛主形态选择：继续小程序、补快应用、补 Android App，还是小程序 + 智能体组合。
2. vivo API 是否作为主模型替换 DeepSeek/Dify，还是只接入关键能力并保留现有模型。
3. `ai-server` 是否继续部署公网，还是逐步把 RAG 编排迁到微信云函数。
4. 是否启用声音复制。若启用，需要设计授权、样音采集、删除音色和隐私说明。
5. 线下资源城市范围是否继续以上海为主，还是扩展到用户定位城市。
6. 新增页面是否继续只写 `.js`，还是按项目要求同步补 `.ts` 文件。

## 12. 建议的下一步

最推荐的下一个开发任务：

**先做 `vivoAigcGateway` 云函数 + 把 `ai-chat` 从本地直连改成云函数调用。**

原因：

- 这是后面语音、OCR、POI、知识库全部复用的底座。
- 能立刻解决真机运行风险。
- 也符合项目“前端调用云函数”的代码规范。

完成后再按顺序做：

1. 文本相似度知识库
2. 短语音识别 + TTS
3. 绘画 OCR/多模态分析
4. POI 资源推荐
5. 快应用/App/智能体展示层
